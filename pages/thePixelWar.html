수천 명의 유저가 실제 지도 좌표를 기반으로 한 무한한 캔버스에 동시에 픽셀 아트를 그리는 상황을 가정한 대규모 트래픽 처리 프로젝트입니다. 모놀리식(Monolithic) 아키텍처에서 발생하는 데이터베이스 병목과 동시성 문제를 극복하기 위해 Redis, Kafka 등 다양한 인프라 기술을 접목하여 실시간 분산 처리 시스템을 구축했습니다.
[Application Modules]
• Auth & User   : Spring Security, Kakao OAuth2
• Pixel Canvas  : Redis + Kafka 활용 비즈니스 로직 및 히트맵 처리
• Chat & Guild  : WebSocket 기반 실시간 소통 및 도안 관리

[Infrastructure & Data]
• Message Queue : Kafka (비동기 Write-Back 패턴)
• Cache & Lock  : Redis (분산 락을 통한 동시성 제어)
• Database      : MySQL, Spring Data JPA
• Storage       : AWS S3 (정적 리소스 관리)

[Deployment & Cloud]
• Cloud Hosting : AWS EC2 (서버 인프라 구축)
• Container     : Docker, Docker Compose (통합 환경 구축)

Trouble Shooting

ISSUE 01

대규모 트래픽으로 인한
DB 데드락 및 병목 현상

🤔 Problem:

수많은 유저가 동일한 픽셀 좌표를 동시에 클릭할 때 동시성 문제가 발생하고, DB에 직접 쓰기(Write) 요청이 몰려 심각한 부하가 발생했습니다.

💡 Solution:

Redisson 기반 분산 락을 적용하여 동시성을 안전하게 제어하고, 즉시 DB에 저장하는 대신 Kafka를 이용한 비동기 Write-Back 패턴을 도입하여 부하를 낮추었습니다. 분산 락 획득 실패 시 예외 처리를 통해 대기열 병목을 방지했습니다.

Distributed Lock & Kafka Event 
String lockKey = "pixel:lock:" + x + ":" + y;
RLock lock = redissonClient.getLock(lockKey);

if (lock.tryLock(5, 2, TimeUnit.SECONDS)) {
    try {
        redisTemplate.opsForValue().set(pixelKey, snappedRequest.color());
        String message = objectMapper.writeValueAsString(snappedRequest);
        kafkaTemplate.send("pixel-updates", message);
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
} else {
    return "다른 사람이 작업 중입니다.";
}
