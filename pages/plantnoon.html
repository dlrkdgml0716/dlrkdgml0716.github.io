[Solution] cancelAtPeriodEnd 플래그와 subscriptionExpiresAt 타임스탬프를 조합하여 설계

Case 02. NoSQL 데이터 구조 선제적 설계

[Foresight] 초기 설계 단계에서 서비스 확장 시 커뮤니티 피드 조회에 따른 N+1 쿼리 문제와 그로 인한 Firebase 읽기 비용 급증 및 네트워크 병목 현상을 선제적으로 예측

[Action] NoSQL의 구조적 특성을 활용하여 기획 단계부터 비정규화(Denormalization) 모델을 채택. likesCount, commentsCount, authorName 등의 빈번한 조회 데이터를 상위 문서에 병합하여 단 1회의 쿼리로 렌더링이 가능하도록 설계

Case 03. 서버 없는 환경에서의 데이터 보안 (Security Rules)

[Problem] 백엔드 서버가 없어, 클라이언트를 통한 데이터 접근·수정을 서버에서 검증할 수 없는 구조

[Solution] 인가 로직 전체를 Firestore Security Rules로 옮겨 서버 사이드에서 강제

  • 개인 데이터(프로필·식물·케어 기록·성장 일지)는 소유권 기반 제어 — request.auth.uid == userId로 본인만 접근, 중첩 서브컬렉션(careRecords, growthDiaries)까지 경로별 명시
  • 관리자 전용 리소스는 isAdmin() 커스텀 함수로 분리 — 사용자 문서의 isAdmin 필드를 get()으로 조회해 판정
  • 커뮤니티 피드(stories)는 읽기 전체 공개 / 쓰기는 인증 회원으로 의도적 완화
firestore.rules
// 공통 관리자 확인 로직의 함수화
function isAdmin() {
  return get(/databases/$(database)/documents/users/$(request.auth.uid)).data.isAdmin == true;
}

// 리소스 성격에 따른 권한 분리 설계
match /stories/{postId} {
  // 커뮤니티 피드: 읽기는 전체 공개, 쓰기는 인증된 회원만
  allow read: if true;
  allow write: if request.auth != null;
}

match /users/{userId} {
  // 사용자 개인정보: 본인 또는 관리자만 접근 가능
  allow read: if isAdmin() || request.auth.uid == userId;
  allow write: if request.auth.uid == userId;

  // 하위 서브 컬렉션까지 소유권 검증
  match /plants/{plantId} {
    allow read, write: if request.auth != null && request.auth.uid == userId;

    // 식물별 케어 기록 및 성장 일기: 데이터 무결성을 위해 개별 경로 명시
    match /careRecords/{careId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    match /growthDiaries/{diaryId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
  }
}

[Applied] 관리자 페이지 진입은 로그인 직후 isAdmin 필드 확인으로 통제(비관리자는 즉시 로그아웃). 이를 우회하더라도 /users 등 개인 데이터 조회는 위 Rules의 isAdmin()이 서버 단에서 차단
